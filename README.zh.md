# REFR/ACT Hackathon Playbook

**阅读语言 / Read in:** [中文](README.zh.md) · [English](README.md)

> 我们想办一场黑客松，是因为相信一个年轻人的想法，值得被认真听见，也值得有机会变成真实的东西。

也许最难忘的时刻，并不是最后的颁奖。是一个原本不敢开口的人第一次说出“我有个想法”；是队友在屏幕前争论、推翻、重来，终于看见原型亮起；是有人发现，自己不仅能使用工具，还能决定工具该为谁、为什么而用。**Reflect，先看见；Refract，换个角度；Act，亲手把可能变成现实。** 这就是我们想为 REFR/ACT 留出的空间。

感动不会凭空发生。要让每个人安心地尝试，报名者得知道去哪里，导师得知道怎么帮忙，评委得知道如何公平地倾听；即使网络断了，也得有人接住。这份 Playbook 是给学生筹备团队的举办 SOP，记录那些不太上镜、却让一场活动真正成立的工作。如果一件事还没人负责、还没获批、还没测试，我们就诚实地写下它，而不是把愿望说成事实。

REFR/ACT 的首届活动计划分两步：先在 PRISMS 做一场约 **4 队**的内部 workshop，测试流程和技术；再根据试点结果，筹备 **2027 年 4 月 17 日（星期六）**的主黑客松。主活动拟在 PRISMS 校园举行，面向 **30–60 名** PRISMS 学生及受邀的周边初、高中学生，每队 **2–5 人**。日期、校内场地、校外参与及具体安排仍需学校确认。

**使用方法：** 每个事项都要有负责人、截止日和状态。表中的时间是倒排参考，不是已经发生的事实。对于不同规模的活动，保留决策顺序，调整人数与周期即可。

## 1. 先决定办什么

黑客松是一次限时的团队项目创作：从问题出发，在有限时间内做出可以演示的原型，并解释为什么这样做。它不是要求所有人写出完整产品，也不只是比谁打字更快。设计、研究、硬件、沟通和验证都应有位置。

在开始拉赞助或发布报名表之前，先把下面六件事写成一页纸：

| 问题 | REFR/ACT 当前方案 | 需要确认 |
| --- | --- | --- |
| 办给谁 | PRISMS 与受邀的周边初、高中学生；预计 30–60 人 | 校外参与范围、容量和准入流程 |
| 什么时候 | 2027 年 4 月 17 日，单日活动 | 校园可用性及最终日程 |
| 在哪里 | PRISMS 校园 | 房间、设备、人员与监督要求 |
| 做什么 | 2–5 人组队，提交原型与简短过程说明 | 题目边界、可用资源 |
| 怎么评 | 每个赛道单独颁奖；同时看作品与过程 | 评委、权重、同分处理 |
| 钱从哪里来 | 筹集现金及实物支持 | 学校财务账户、审批与报销方式 |

**暂停点：** 如果场地、校外学生进入校园的规则、现场监督、财务路径尚未明确，不要对外宣布这些内容已经确定。可以继续准备方案和意向名单，但不要出售一个团队无法兑现的活动。

## 2. 谁来负责

小团队最怕“大家都会做”，最后变成“没人真正接”。建议 **5–7 名学生核心组织者**，可以一人兼两岗，但每项工作只设一位最终负责人。

| 岗位 | 必须交付的东西 |
| --- | --- |
| 总协调 | 总时间线、每周会议、决策记录、风险清单；把待学校确认的问题集中提出 |
| 学校对接 | 场地、faculty advisor、proctors、校外学生、访客及家长许可流程 |
| 活动与参赛者 | 报名表、确认邮件、赛道规则、导师/评委沟通、现场答疑 |
| 技术 | Wi-Fi、电源、投影、提交系统、AI/API 访问与负载测试 |
| 合作与财务 | 赞助沟通、权益记录、预算版本、学校账户及采购/报销手续 |
| 现场执行 | 房间图、物资、签到、餐饮、时间提醒、突发情况联络 |

每周 20–30 分钟即可，但会议结束时应留下三样东西：**谁做、何时交、卡在哪里**。重要决策写进同一份共享记录；不要只留在聊天记录里。

## 3. 倒排时间线

| 时间 | 这一阶段结束时，应该已经有 |
| --- | --- |
| T−12 至 T−10 周 | 一页活动定义；学校对接人；初步场地和校外参与可行性；预算草案 |
| T−10 至 T−8 周 | 内部 workshop 方案与日期；报名/许可路径；潜在赞助与社区伙伴清单 |
| T−8 至 T−6 周 | 跑完 workshop；记录技术、评审和流程问题；修订主活动规则 |
| T−6 至 T−4 周 | 获准后发布主活动报名；确认导师/评委邀约；提交系统可用 |
| T−4 至 T−2 周 | 参赛名单、房间布局、食物数量、物资订单、志愿者排班 |
| T−14 至 T−7 天 | 第二轮技术测试；安全与访客流程；所有参与者收到活动指南 |
| T−7 至 T−1 天 | 现场走查、打印备份、最终人员确认；冻结规则版本 |
| T 日 | 执行日程、记录异常、收齐提交、评审和颁奖 |
| T+1 至 T+14 天 | 致谢、项目归档、财务结算、匿名反馈、复盘和公开总结 |

不要为了赶时间跳过试点。试点不是缩小版颁奖活动，而是为了找到主活动中最容易失效的环节。

## 4. 校内试点：先跑一遍

**形式：** PRISMS Internal Workshop，日期待定，约 4 队 PRISMS 学生。具体学生人数由队伍规模决定，不预设人数。

把它当作一次带观察记录的排练：

- [ ] 用更简单、边界更清楚的项目提示，试跑 **Reflect / Refract / Act** 三个赛道的说明。
- [ ] 观察学生在哪里使用 AI：提出问题、查资料、写代码、设计、调试，还是修改方向。
- [ ] 让每队提交短反思：AI 给过什么建议？哪些被接受、拒绝或修改？哪项关键判断是人做的？
- [ ] 用拟定评审表试评项目，找出措辞含糊或无法区分作品的问题。
- [ ] 测试签到、分组、时间提醒、提交、Demo 与反馈的实际耗时。
- [ ] 测试学校电脑、可用的免费/批准 AI token、本地模型等路径；哪些能用，哪些不稳定，分别记下来。
- [ ] 通过 workshop 使用情况和/或单独负载测试，评估可用基础设施能否可靠支撑**约 24 个同时进行的 AI 会话**。这是待测目标，不是已确认能力。

**试点结束后 48 小时内开复盘会。** 每个问题只写三栏：观察到什么、对 4 月 17 日有什么影响、由谁在何时修正。至少修订一版规则、技术方案和现场流程，再扩大到主活动。

## 5. 场地、人员与审批

向学校提出一份集中、可回答的需求清单，不要在不同邮件里零散追加。

| 需要学校协助确认 | 为什么现在要问 |
| --- | --- |
| 4 月 17 日场地与容量 | 主工作区、开闭幕/Demo 区、导师或 workshop 空间、休息/餐饮区；如做硬件，再确认实验室或工程空间 |
| Faculty advisor、学校活动联系人、proctors | 学生组织者不能代替学校现场监督；proctors 人数及职责由 PRISMS 确定 |
| 评委安排 | 计划约 3–4 位评委；确认校内参与、外部评委准入及评审时段 |
| 财务账户与负责人 | 接收赞助、记录资金、批准采购/报销、发放奖项；不使用学生个人账户代收活动资金 |
| 校外参与者 | 邀请范围、访客登记、家长许可、接送、校内活动规则及紧急联系方式 |
| IT 与设备 | Wi-Fi、电源、显示设备、学校电脑/AI 访问及提前测试；技术支持计划约 1–2 人 |
| 其他现场人员 | 导师约 3–5 人；签到/后勤约 2–3 人；最终人数随学校要求及批准的参赛人数调整 |
| 餐饮与安全 | 食物供应、过敏信息、清洁、出入控制、急救与紧急联系人 |

**交付物：** 一张经学校确认的房间图、一份联系人/职责表、一版允许对外发布的活动信息。以上都未确认前，在公开材料中使用“拟定”“待确认”，不要写成学校承诺。

## 6. 预算与合作伙伴

先列成本，再谈赞助。否则容易得到一堆兑换码，却缺少真正需要的物资或可用现金。

**预算至少分五栏：** 奖项、餐饮、硬件/耗材、宣传与现场物资、备用金。每项标注数量、估价、支付方式、审批人，以及“必须有 / 可以削减”。报价和最终采购都按学校流程执行。

REFR/ACT 的当前筹资目标是**现金与实物合计 $10,000+**，其中潜在学生奖池目标为 **$3,000+**。它们是目标，不是已获得款项，也不代表 PRISMS 承诺出资；最终赞助和奖项方案需学校批准。

按提供的资源来分类，比只按公司大小分类更有用：

| 类别 | 适合沟通的支持 | 联系时要确认 |
| --- | --- | --- |
| 云算力 / AI 工具 | 如 AWS 等提供云额度、API/token、技术人员或 workshop | 额度是否可给未成年人/学校使用、有效期、并发限制、数据规则 |
| 孵化器 / 创业社区 | 如 YC 相关创业者网络提供导师、评委、项目反馈或引荐 | 谁实际到场、时间、是否与学生项目有利益冲突 |
| 开发者 / 本地社区 | 社区宣传、志愿者、导师、工作坊或场地资源 | 宣传范围、联系人、入校与未成年人活动规则 |
| 硬件 / 开发工具 | 开发板、传感器、软件授权、设备借用或奖品 | 运输、损坏责任、兼容性、现场技术支持 |
| 现金赞助 | 覆盖奖项、耗材、餐饮与必要开支 | 付款路径、学校审批、可提供的致谢方式 |

**赞助沟通最小记录：** 机构、联系人、提出的具体需求、可能提供什么、限制条件、下一步和负责人。不要把“发过邮件”算作已获赞助；收到书面确认并通过学校流程后再计入可用预算。赞助权益保持真实：品牌致谢、产品试用、技术分享或项目反馈可以讨论，学生招聘或对学生作品的默认所有权不在方案里。

## 7. 报名与参与者沟通

报名页要让第一次参加黑客松的学生也看得懂：什么是活动、谁能参加、日期地点、队伍人数、三个赛道、需要带什么、是否有餐食、如何取得许可，以及什么时候收到确认。

只收组织活动所需信息；未成年人个人资料按学校要求保存与使用。公开名单、照片及项目展示需遵守同意和学校规则。

建议至少发送三封信息：

1. **报名确认：** 收到了什么、何时公布结果、联系渠道。
2. **行前指南（约一周前）：** 报到时间、地图、队伍/赛道选择、设备、软件、家长/访客要求、餐饮说明。
3. **前一天提醒：** 最终时间地点、迟到或取消怎么办、现场联系人。

预留候补名单。有人退出时，按既定顺序补位，不在私信里临时改变规则。

## 8. 技术与物资

技术测试要用**学生实际会走的路径**，而不是组织者自己的管理员账户。提前让一台普通学生设备从连接 Wi-Fi 开始，完成登录、访问 AI/API、提交项目的全流程。

- [ ] Wi-Fi 在主要房间的覆盖与并发；有访客网络时，确认校外学生能否使用。
- [ ] 插座、延长线、走线方式、充电安全；不把通道变成电缆区。
- [ ] 投影、转接头、音频、计时屏和备用演示方式。
- [ ] 提交表单/仓库链接、截止时间、文件格式、上传后确认回执。
- [ ] AI 与 API 的账号发放、费用上限、速率限制、token 用尽后的替代路径。
- [ ] 本地模型或学校基础设施的可行性与约 24 并发会话负载测试结果。
- [ ] 硬件套件、工具借还、耗材、损坏和清点流程。
- [ ] 纸质签到表、离线日程、评委评分表、紧急联系人备份。

每次测试记录日期、设备/账号、步骤、结果、故障和修复人。“已经开通过账号”不等于“参赛者现场能用”。

## 9. 赛道、提交与评审

**Reflect、Refract、Act 是三个可分别报名、分别颁奖的赛道（tracks），不是要求每队依次完成的三个阶段。** 三个名字也提示我们共同的工作方式：先理解问题，再换视角审视，最后做出并测试东西。参赛队选择最符合项目重心的一个赛道；若项目跨赛道，报名截止前确定主赛道，避免赛后为奖项重新分类。

| 赛道 | 核心问题 | 评委应看到的证据 |
| --- | --- | --- |
| **Reflect** | 你是否找对了值得解决的问题？ | 目标使用者、真实需求、假设检验，以及原型如何回应需求 |
| **Refract** | 不同视角或 AI 工具是否真正改变了你的判断？ | 至少一个被比较的方案、被接受/拒绝/修改的建议，以及改变原因 |
| **Act** | 你的想法能否落地并经受测试？ | 可运行/可演示原型、测试或迭代记录、技术决策与局限 |

每个赛道仍要同时看**结果**（有用性、技术执行、创造性、原型质量）和**过程**（问题理解、推理、不同视角、AI 使用判断）。不要把 Reflect 变成只交调研报告，或把 Act 变成只比完成度；所有队伍都要做出能够演示的东西。

**统一提交包：** 项目名称、队伍成员、所选赛道、一句话问题定义、Demo 链接/现场演示、做过的主要决定，以及一段简短的 **AI Process Reflection**：AI 在哪里参与？有什么输出被拒绝或改写？哪些判断由团队自己完成？没有使用 AI 的队伍也可以说明原因，不必为了填表而使用。

**评审前必须定稿：** 评分项与权重、每个赛道的奖项数量、评委回避规则、同分处理、迟交处理、是否允许赛前代码/项目基础，以及是否允许跨队协作。评委拿到同一版规则和简短校准示例，再开始打分。奖项预算和发放路径经学校确认后公布。

## 10. 活动当天怎么运行

下面是单日活动的**示例节奏**，不是最终排期。学校时间、房间和监督安排确认后再落具体钟点。

| 顺序 | 现场负责人要做什么 | 完成标志 |
| --- | --- | --- |
| 开门前 | 测 Wi-Fi、投影、提交入口；摆好签到、引导、饮水和电源区 | 普通学生设备能走通全流程 |
| 签到 | 核名单与许可；分发日程、规则和求助渠道 | 每队知道位置与联系人 |
| 开场 | 讲清三个赛道、提交内容、时间点、行为与安全规则 | 规则链接已发给所有队伍 |
| 组队/确认项目 | 协助未组队学生；确认队伍、赛道与项目问题 | 有队伍清单，人数符合规则 |
| Build | 导师巡场，组织者看时间、技术问题、餐饮与房间秩序 | 问题有人接、有人记录 |
| 截止前提醒 | 提前两次提醒提交格式与截止时间 | 参赛队能看到提交回执 |
| Demo 与评审 | 按固定顺序和统一时长展示；收齐评分 | 所有有效队伍都获得同等展示机会 |
| 颁奖与结束 | 各赛道分别宣布结果；说明后续反馈与离场安排 | 奖项记录、设备回收、人数核对 |

现场用一张共享运行表：**时间、动作、负责人、备用人、状态**。临时决定（如延长提交时间）要对所有队伍同时公布，并记录是谁、何时做出的决定。

## 11. 出了问题怎么办

先保证人和规则的公平，再处理展示效果。问题发生时，指定一位现场负责人统一对外说明，避免三个组织者给出三种答案。

| 情况 | 第一反应 | 后续决定 |
| --- | --- | --- |
| Wi-Fi / AI 服务不可用 | 记录开始时间和影响队伍；切到本地/离线或备用工具 | 是否统一延时，由同一负责人通知全场 |
| 提交系统故障 | 启用备用表单或邮件/离线收件，保留时间戳 | 所有队伍适用同一补交规则 |
| 导师/评委缺席 | 按预先排好的候补名单补位 | 重新核对评审时长与回避关系 |
| 队伍人数变动 | 核查规则与许可，不现场口头豁免 | 在截止前统一处理并记录 |
| 安全、健康或学生离场问题 | 立即联系学校指定 proctor / 校方应急联系人 | 由学校流程决定下一步；活动节奏让位于学生安全 |
| 预算或赞助临时变化 | 冻结未批准的采购/承诺 | 按“必须有 / 可削减”预算重新排优先级 |

## 12. 收尾与复盘

活动结束不等于工作结束。最好在大家记忆还新鲜的两周内完成：

- [ ] 核对设备归还、场地清理、采购发票、赞助履约和奖项发放。
- [ ] 给参与者、导师、评委、学校联系人、赞助与社区伙伴发送具体致谢。
- [ ] 经同意后发布项目与照片；未授权的个人信息不进入公开仓库。
- [ ] 发一份短反馈表：最有帮助的环节、最卡住的环节、是否会再参加。
- [ ] 复盘报名到场、技术故障、提交率、各赛道评审耗时、预算偏差。
- [ ] 每项改进都写成“下次怎么改 + 谁负责”，而不是“沟通需要加强”。

**判断活动有没有办好，不只看 Demo 有多亮眼。** 看学生是否能说清楚自己为谁做、为什么这么做、哪些建议没有采纳；也看第一次参加的人是否得到足够支持，看团队是否把临时故障处理得公平。

## 给下一届组织者

如果有一天，你接过这份清单，请不要先担心自己能否办出一场“完美”的活动。先找到愿意同行的人，找到可信的学校联系人，把第一次测试做小；把不知道的事说出来，再一件一件解决。

我们希望有学生带着一个模糊的问题走进来，带着“原来我也可以”的确信走出去。希望那些替别人搬桌子、查线路、改规则、熬夜写邮件的人，也能在某个瞬间看见：自己的认真，给了别人勇敢尝试的机会。

如果这份 Playbook 能让下一届少走一点弯路，让更多想法被听见、被检验、被实现，那么所有看似琐碎的准备，就都有了意义。**愿我们始终记得，真正让 REFR/ACT 发光的，不是舞台上的灯，而是站在灯下和灯外的人。**
